# PRD — Aaron's Portfolio: "From Idea to Experience"

## 1. Product

An interactive personal portfolio for **Aaron, Frontend Developer**, built as **one continuous scroll-driven story**, not a set of sections.

**Positioning:** "Frontend Developer focused on turning ideas, designs, and requirements into thoughtful digital experiences."

**Narrative spine:** Idea → Mindset → Process → Product → Playground → Contact

**The site must prove Aaron can:**
- Read a PRD and work from existing UI/UX designs
- Work independently when no designer exists (research → UX direction → design system → UI)
- Build 0 → 1 and improve existing products
- Define typography, color, and component systems
- Choose appropriate tech and ship responsive, accessible, performant work

The portfolio itself is the primary evidence. It must not read as "Aaron knows React"; it must read as "Aaron bridges design, product thinking, and frontend engineering."

**Visual direction:** Technical Minimalism — editorial, modern, premium, cinematic, interactive. Priorities in order: visual hierarchy → readability → interaction clarity → narrative continuity.

---

## 2. Scene 01 — The Idea

**Heading:** "Everything starts with an idea."

**Purpose:** Establish that products begin with an idea, problem, users, and requirements — not code.

**Content sequence:**
1. Minimal canvas: `NEW PROJECT` / `What's the idea?` + empty input-like visual
2. On scroll, concepts appear and self-organize: problem, user, idea, requirements
3. They assemble into a structured project brief (real example: OLM real estate platform — project name, product type, goal)
4. The brief progressively resolves into an interface

**Required transformation logic:** Idea → Information → Structure → Interface. Every visual step must be legible as part of the product-making process.

**Exit:** "So, how do I turn an idea into an experience?" → Scene 02.

**Reject:** abstract or random transformations that don't map to the process.

---

## 3. Scene 02 — The Mindset

**Copy:**
> I'M AARON. A Frontend Developer focused on turning ideas, designs and requirements into thoughtful digital experiences.
> I care about the details. How it looks. How it feels. How it behaves. How it works.

**Primary element:** a **scroll-scrubbed cinematic video**. Scroll position drives the timeline — down advances, up reverses, slow scroll = slow progression. It must feel like a product film, not a screen recording or tutorial.

**Seven phases in the video:**

| Phase | Tagline | Shows |
|---|---|---|
| Understand | Make it clear | Problems, requirements, users, information hierarchy, user flows, goals |
| Design | Make it feel right | Typography, color, spacing, hierarchy, composition, visual direction |
| Experience | Make it easy to use | Navigation, interactions, states, feedback, responsive behavior. Motif: CLICK → FEEDBACK → STATE CHANGE → USER UNDERSTANDS |
| System | Make it consistent | Tokens, components, patterns, type scale, colors, spacing, buttons, inputs, cards, nav, states, responsive rules |
| Build | Make it work | DESIGN → COMPONENT → REACT → TYPESCRIPT → API → APPLICATION |
| Tools & Libraries | The right tool for the right problem | Grouped by purpose, never a logo wall — UI: Next.js, Tailwind · Motion: GSAP, ScrollTrigger, Lenis · Dev: TypeScript, Git, GitHub · Design: Figma · Data: PostgreSQL, REST |
| Refine | Make it better | BUILD → TEST → FIND → IMPROVE → POLISH — responsive testing, edge cases, loading/error states, a11y, performance, polish |

**Convergence:** UNDERSTAND → DESIGN → EXPERIENCE → SYSTEM → BUILD → REFINE → PRODUCT.

**Exit:** end on a final product visual that reads as a real interface and carries into Scene 03.

---

## 4. Scene 03 — The Process

**Heading:** "Every project starts differently."

**Format:** scroll-scrubbed video + animated web overlays + workflow diagrams.

**Three entry points:**
1. **PRD to Frontend** — PRD → UI/UX → Design System → Components → Frontend → Integration → Full Product. *Proves:* can translate requirements and existing designs into a shipped frontend.
2. **PRD Without UI/UX** — PRD → Research → UX Direction → Design System → UI → Components → Frontend → Product. *Proves:* independence with no designer.
3. **From Zero** — Idea → Problem → Research → UX → Design → Design System → Frontend → Product. *Proves:* full 0 → 1 capability.

All three converge into one shared path: PRD and/or RESEARCH → YOU → DESIGN + UX → DESIGN SYSTEM → COMPONENTS → FRONTEND → PRODUCT.

**Exit into Scene 04 (specified deliberately):**
- Hold the final frame on the completed product for a beat
- Keep the product visually present as Scene 04 enters
- Allowed: subtle shifts in scale, position, opacity, background, typography, surrounding layout
- **Forbidden:** zooming the product toward the viewer, making it interactive, turning it into a product demo, dramatic or abrupt transformation
- Message conveyed: "This is the product we just saw being built. It actually exists."
- Order of understanding: recognize the product → know what it is → know Aaron's role
- Do not introduce another workflow, design system, or process block here — already covered

## 5. Scene 04 — The Work

**Heading:** "Things I've actually built."

Begins directly from the held product of Scene 03 — a continuation, not a section break.

**Per-project reveal order:** product visual → title → concise description → role and contribution → technologies → further detail.

**Each project must state:** what the product is, Aaron's role, what he built, what he cared about, technologies, and outcome where applicable. Relevant angles: UX, responsive design, design systems, component architecture, interaction, accessibility, performance, polish.

**Example metadata format:** `OLM — REAL ESTATE PLATFORM — React — Laravel — Tailwind — Frontend Engineer — 2024`

**Structure:** each project is its own visual chapter in a vertical sequence of immersive stories. The current project leaves the viewport as the next enters — the next reads as the same story continuing, not a new page.

**Assets:** real screenshots, project videos, real interface states, mobile views, genuine UI detail.

**Reject:** a conventional grid of cards as the primary presentation; effects that outweigh the work itself.

**Flow:** COMPLETED PRODUCT → INTRO → DETAILS → EXPERIENCE → NEXT PROJECT → …

## 6. Scene 05 — The Playground

**Heading:** "Play with it."
**Sub:** "A few things I like to build when I'm not building products."

Lightweight experiments only — not a game, not a complex technical demo. Visually continuous with the rest of the site.

| Experiment | Interaction | Demonstrates |
|---|---|---|
| Type | "TYPE IS AN EXPERIENCE." with live controls: size, weight, letter spacing, line height | Typography and hierarchy |
| Color | Live controls: primary, secondary, background, text | Color systems and visual relationships |
| Motion | Interface responding to cursor, hover, transitions, scroll — subtle and intentional | Interaction and motion design |
| Component | States: DEFAULT, HOVER, ACTIVE, LOADING, SUCCESS, ERROR | Component behavior and states |
| Responsive | Browser-like frame with draggable width across desktop / tablet / mobile | Responsive design thinking |

## 9. Acceptance Criteria

The build is complete when:

1. The six scenes read as one continuous experience; every major transition is intentional and preserves narrative continuity.
2. Scroll-scrubbed video in Scenes 02 and 03 responds to scroll direction and speed, and holds its final frame into the next scene.
3. The Scene 03 → 04 handoff follows the specified rules, including the forbidden list.
4. Every project in Scene 04 answers: what it is, Aaron's role, what he built, what he cared about, tech, outcome.
5. All five playground experiments work and share the site's visual language.
6. The experience holds up at large desktop, desktop, laptop, tablet, mobile, and small mobile — each intentionally designed, not scaled down.
7. `prefers-reduced-motion` is respected with all content and navigation still fully usable.
8. The site remains usable when animation is reduced, media fails, or the device is limited.
9. Every scene maintains readability, usability, hierarchy, interaction clarity, performance, accessibility, and cinematic quality.

**Standards for 6–9 are defined in `claude.md` and are binding.**

---

## 10. Out of Scope

- Blog, CMS, comments, analytics dashboards
- Multi-page routing that breaks the single continuous experience
- Technologies not actually used in the final build (never show a tool Aaron didn't use)
- Database dependency for static content
- Effects that exist only to impress
